---
title: "Use Orca from coding agents"
description: "Run orca mcp serve so Claude Code, Cursor, and Codex can manage and talk to your Orca agents."
---

`orca mcp serve` runs an MCP server on stdio with one tool per CLI action. A coding agent can then list models and create agents, start sessions and chat with them, put files in a session's sandbox and download what it made, manage skills, vaults, and files, read and copy Orca's kits, and read usage and your wallet, all as you.

It uses the CLI's own login, read again on every call, so you can add it before you sign in. Sign in first with [`orca login`](/cli/install#sign-in). Without a key, each tool answers "not logged in to Orca." and how to log in.

## Claude Code

Install the Orca plugin. It adds the `use-orca` skill and registers the MCP server for you:

```bash
claude plugin marketplace add okikorg/orca-cli
claude plugin install orca@orca
```

Or register only the MCP server:

```bash
claude mcp add orca -- orca mcp serve
```

## Cursor

Add the server to `~/.cursor/mcp.json` for every project, or `.cursor/mcp.json` for one:

```json
{
  "mcpServers": {
    "orca": {
      "command": "orca",
      "args": ["mcp", "serve"]
    }
  }
}
```

## Codex

```bash
codex mcp add orca -- orca mcp serve
```

Or add it to `~/.codex/config.toml`:

```toml
[mcp_servers.orca]
command = "orca"
args = ["mcp", "serve"]
```

## The tools

| Area | Tools |
| --- | --- |
| Identity and keys | `whoami`, `list_keys`, `create_key`, `revoke_key` |
| Agents and models | `list_agents`, `get_agent`, `create_agent`, `update_agent`, `delete_agent`, `list_models` |
| Sessions | `list_sessions`, `get_session`, `create_session`, `list_session_items`, `delete_session`, `sleep_session`, `chat`, `list_artifacts`, `download_artifact` |
| Skills | `list_skills`, `get_skill`, `create_skill`, `delete_skill` |
| Vaults | `list_vaults`, `create_vault`, `delete_vault`, `list_credentials`, `add_credential`, `delete_credential` |
| Files | `list_files`, `upload_file`, `download_file`, `delete_file` |
| Usage and billing | `get_usage`, `list_usage_events`, `get_wallet`, `billing_checkout`, `billing_portal` |
| Kits | `show_kit`, `copy_kit` |

`chat` sends a message to an agent or session and waits for the reply, by default up to 120 seconds and at most 600. It returns the session ID, whether the turn finished, its status, and the reply, so the coding agent can continue the same session.

For a new session, `chat` also takes `sandbox`, `template`, and `vaults`, as `create_session` does. `template` and `vaults` take IDs or names, so an agent that needs an environment template and a vault starts with one call, for example `chat({agent: "researcher", template: "research", vaults: ["orders"], message: "..."})`. A session you continue keeps its own sandbox and vaults, so these three are refused alongside `session`.

`chat` and `create_session` take `files`, a list of `{path, dest}` on your machine, and put them in the session's sandbox as [`--file`](/cli/commands#files-in-and-out-of-a-sandbox) does. `list_artifacts` and `download_artifact` bring back what the agent saved under `/workspace/outputs`: one artifact by ID or path, or with `all` every file of the newest turn into a folder.

`sleep_session` puts a session's sandbox to sleep now. Files in `/workspace` are saved and machine time stops; the conversation stays, and the next message wakes it. Running programs stop and do not come back. It is refused while a turn runs. It waits up to 60 seconds and returns `state` and `last_sleep`; `get_session` includes `sandbox`, the sandbox's state. These need CLI 1.5.0 or later; see [put a sandbox to sleep now](/guides/environments#put-a-sandbox-to-sleep-now).

`show_kit` returns a kit's review: what it runs, reaches, and spends, then each agent, skill, and template in full, and the `version` it describes. `copy_kit` takes `publicId`, that `version`, and `assets`, and copies nothing if the kit has changed since. Have the coding agent show you the review first, and copy only after you say yes. These two need CLI 1.4.0 or later; see [kits](/kits).

`add_credential` takes `type`: `static_bearer` (the default) with `token`, or `static_basic` with `login` and `password`, which Orca sends to the server as HTTP Basic (see [a login and password](/guides/credentials#a-login-and-password)). Its `vault` is the vault's ID.

<Warning>
A password is better typed in a terminal than passed through a coding agent: anything sent in a tool call sits in the agent's context. Have the agent give you the command, `orca vaults credentials add <vault> --name <name> --server <url> --basic --login <login>`, and run it yourself; it reads the password at a hidden prompt.
</Warning>

`list_models` returns one row per model name, with who pays and, for Orca credit, OpenRouter's price. The list is long, so it pages with `limit` and `after`, and `query` (part of a name, such as `luna`) or `payer` narrows it.

Commands that only touch your machine (login, logout, context, doctor, update) have no tool. Tools act with your key's role, so admin-only actions fail for a member.

## In practice

Ask your coding agent things like:

- "Create an Orca agent called reviewer on `orca/openrouter/openai/gpt-5.6-luna` that reviews pull request descriptions."
- "Chat with reviewer about this diff and give me its answer."
- "Give the analyst agent `sales.csv`, ask it for a chart, and download the chart here."
- "How much Orca credit do I have left?"

Treat what the agent does with these tools as you would any command it runs: it can create, delete, and spend on your behalf.
